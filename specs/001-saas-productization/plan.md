# 企业 AI 工作台服务化路线——实施计划

**功能编号**：`001-saas-productization`
**修订日期**：2026-09-19
**依据**：[需求规格](./spec.md)
**状态**：产品交付版，可执行

> 编号说明：本文件的“实施阶段”用于安排任务依赖，不等同于 PRD 中的四个“产品阶段”。例如，“稳定产品基线”属于当前产品第一、二阶段的完善工作，不是一个对外产品版本。

## 1. 计划摘要

实施顺序调整为：

```text
稳定产品基线
    ↓
资料授权与安全接入（敏感或多人试点前）
    ↓
一个单租户真实或内部试点
    ↓
按真实阻塞项补版本、协同归档或一个连接器
    ↓
第二次独立交付验证可复制性
    ↓
共享多租户、接口和用量计量
```

与旧计划相比，本版删除了“先建设共享基础设施再试点”的前置工作，也不再把 PostgreSQL、对象存储、任务系统、OIDC、行级安全和 pgvector 同时列为近期交付。它们是候选技术方案，只有对应问题真实出现时才进入实现。

## 2. 路线调整结论

| 旧安排 | 问题 | 新安排 |
|---|---|---|
| 真实试点前先建设数据库、对象存储和任务系统 | 投入大，不能证明用户价值 | 当前只修复影响验证和试点的稳定性问题 |
| 用 2–3 家企业作为第一阶段前提 | 前置成本过高，也无法由当前仓库证明 | 先完成 1 个真实或内部团队试点，再验证第二次交付 |
| 权限、连接器、多租户放在同一阶段 | 安全边界、接入方式和商业模式混在一起 | 先做单租户企业交付，再决定共享多租户 |
| 102 个任务覆盖完整平台化 | 任务密度高于当前证据，容易稀释核心目标 | 只保留近期可执行任务，远期保留门槛与验收 |
| AI 前沿资讯与核心路线并列 | 与制度问答的付费问题关联较弱 | 保留为辅助页面，不作为近期投资重点 |

## 3. 实施原则

1. **先价值，后平台**：先证明员工愿意使用、答案能解决问题、运营成本可接受。
2. **先独立部署，后共享租户**：独立部署可以完成价值验证，也降低早期隔离风险。
3. **先关闭真实阻塞，后补全能力清单**：试点未被某项能力阻塞时，不提前建设。
4. **技术服务于产品证据**：检索、权限和架构细节用于解释产品选择，不偏离核心产品目标。
5. **保持诚实边界**：样例数据、离线指标、当前界面和计划能力分别标注。
6. **安全先于试点**：真实身份、资源授权和必要审计不是先试用后再决定的功能；涉及敏感或多人访问必须前置。

## 4. 当前架构判断

### 4.1 近期保留

- 保留 FastAPI、Streamlit 和模块化单体，避免无收益重构。
- 保留当前本地索引和文件存储，用于单租户价值验证。
- 保留混合检索、证据门控、引用、拒答、反馈、评测和合同独立知识边界。
- 让自动化回归使用确定性证据组织，产品运行继续使用配置的大模型。

### 4.2 试点触发后再决定

| 真实问题 | 候选方案 | 决策证据 |
|---|---|---|
| 文档更新频繁且需回滚 | 不可变文档版本、候选索引和发布指针 | 试点中出现版本冲突或回滚需求 |
| 开始敏感、多人或远程试点 | 企业身份、角色与资源授权、审计 | 进入该场景即触发，不能延后到扩围 |
| 文档来自网盘或办公平台 | 一个需求最明确的连接器 | 人工更新成为主要运营成本 |
| 同一服务承载多个企业 | 租户上下文、隔离存储、隔离任务和测试矩阵 | 至少两次交付证明共性且共享有收益 |
| 需要嵌入客户门户 | 版本化接口、稳定错误码、幂等和限流 | 客户有明确集成方与使用路径 |
| 需要商业结算 | 可去重的用量事件和对账 | 定价假设和付费意愿已有证据 |

## 5. 分阶段计划

### 阶段零：稳定产品基线（现在执行）

**目标**：让当前已实现闭环稳定、可复现、可讲清。

**交付物**：

- 稳定的全量测试、固定检索评测和回答质量回归；
- 10 个手工问题的逐题审计，覆盖复合问题完整性和无关内容排除；
- 产品评审说明和三类问题清单：产品判断、质量验证、SaaS 路线；
- README、PRD、路线图和 Spec Kit 文件的一致事实边界。
- 工程采购合同合成样本、12 类核对、人工备注与导出；独立合同集效果仍待验证。

**退出门槛**：自动化验证通过；核心验收路径不依赖外网；所有成果表述能指向代码、页面或报告。

### 阶段一：单租户试点（有资料和负责人后启动）

**目标**：用一个真实企业或内部业务团队验证价值与运营成本。

**最小范围**：

- 先满足资料来源与分发依据、有效版本和部署边界；多人或敏感资料先执行 T022–T025、T027 的安全接入与验收；
- 仅导入已授权的真实或脱敏制度；合同是否进入试点单独审批；
- 建立 20–50 个真实问题的验收集；
- 记录问题解决、人工转接、知识更新和坏例归因；
- 用独立部署完成交付，不要求多租户。

**退出门槛**：至少一个完整观察周期；业务负责人愿意继续试用或扩大范围；已形成按影响排序的真实阻塞清单。

### 阶段二：企业交付能力（按阻塞项启动）

**目标**：安全接入项在试点前完成；其余能力关闭实际观察到的版本、协同和接入问题。

**推荐顺序**：

1. 企业身份、检索前权限过滤、必要审计和恢复（敏感或多人试点前置）；
2. 文档版本、候选验证、发布与回滚（按更新风险）；
3. 首个真实需要的文档连接器；
4. 备份恢复、运行监控和故障处置。

非安全扩展按实际阻塞排序；不得用“价值尚待证明”为理由绕过安全前置条件。

**退出门槛**：阻断试点扩围的问题已关闭；越权和资源枚举测试无泄露；文档更新失败可回退。

### 阶段三：共享 SaaS（第二次独立交付后评估）

**目标**：把已经重复出现的交付能力产品化，而不是把定制项目硬改成平台。

**候选范围**：

- 服务端租户上下文和全链路租户隔离；
- 版本化接口、幂等、限流和参考客户端；
- 租户生命周期、配额、用量事件和运营汇总；
- 共享存储和检索方案，具体技术通过容量与隔离验证选择。

**退出门槛**：双租户隔离矩阵无泄露；独立部署可迁移和回滚；共享方式具有明确成本、交付或运维收益。

## 6. 验证策略

| 层级 | 验证内容 | 当前用途 |
|---|---|---|
| 自动化测试 | 解析、检索、证据门控、接口、合同访问边界 | 防止代码回归 |
| 固定检索评测 | Hit@1、Hit@3、MRR、拒答、引用和文档覆盖 | 检索链路代理指标 |
| 回答质量回归 | 必答关键词、拒答和语料适配消融 | 稳定已知问法，不等同真实正确率 |
| 手工逐题审计 | 必答事实、禁止事实、来源和完整性 | 检查复合问题和答案污染 |
| 浏览器端到端检查 | 员工路径、运营路径、身份切换和手机布局 | 保障核心路径可用性 |
| 真实试点指标 | 使用、解决、转接、更新成本、续用意愿 | 决定是否继续产品化 |

## 7. 产品评审结构

1. **背景**：制度分散、重复答疑、通用回答难核验。
2. **选择**：以制度问答为切口，来源引用和拒答作为信任机制。
3. **实现**：文档处理、混合检索、证据判断、模型回答、反馈评测。
4. **验证**：展示自动化测试、离线评测和一条人工坏例分析。
5. **局限**：样例语料、单租户、本地身份边界、无真实业务指标。
6. **下一步**：先满足安全接入，在单租户试点测真实效果，按阻塞补企业能力，再评估共享服务。

## 8. 主要风险

| 风险 | 表现 | 处理 |
|---|---|---|
| 产品范围过大 | 新闻、ERP、人事、合同、多租户同时推进 | 主线聚焦制度问答，合同作为扩展，其他只说明边界 |
| 自动化结果不稳定 | 测试受本机模型措辞影响 | 固定事实回归使用确定性证据组织 |
| 离线高分被误解 | 把固定案例满分说成生产准确率 | 同时展示案例数、口径、坏例和限制 |
| 技术方案喧宾夺主 | 大量讨论数据库和租户架构 | 先说明用户问题和阶段门槛，技术细节放入专项评审 |
| 未来路线被误解为已完成成果 | 使用“已支持、已上线”等措辞 | 统一使用“计划、候选、启动条件” |

## 9. 完成定义

本路线文档完成，不等于 SaaS 已完成。只有对应阶段的代码或流程、验证证据、复现命令和边界说明同时存在，才能把该阶段标记为已交付。
